### Spec and task alignment
- The original defect (three rows, tight Courier block) is closed and genuinely pinned: I ran `make check` fresh — **409 passed, 19 skipped, coverage 84.88 %**, ruff/mypy clean.
- The tests are better than most: I ran five mutations of my own against the regression file and each turned the suite red in the right place (height test dropped → the 2 tight-block refusal rows; width test dropped → 13 failed; `same_line` guard dropped in the refusal helper → 13 failed; trim margin `0.01 → 0` → the collapse row; the `other.contains(centre)` skip removed → 26 failed). Tree restored afterwards.
- What the suite cannot see is **how the target is identified**. The fitter takes "the first span whose bbox contains the rect's centre" and builds every later decision (which neighbours to trim against, which glyphs must stay reached) on it. Every fixture is a non-overlapping stack of lines, so that assumption is never violated in the tests. It is violated by (a) any large text object under the target (watermark, stamp) and (b) leading below ~0.7 em, and both reproduce below.
- `features.json` f9 and `verification.md` state that a block with leading tighter than its glyph height "is REFUSED rather than converted with a line lost", and the verification table answers "is leading/font below 0.8 in scope? **yes**". Finding 2 falsifies that over a wide range.
- Scope: `verification.md` says "Nothing else rides along", yet the diff against the base also carries a release bump (`.release-please-manifest.json`, `backend/CHANGELOG.md`, `pyproject.toml`, `server.json`) and lessons 021/022 about a release-PR conflict. Harmless, but the claim is false as written.
